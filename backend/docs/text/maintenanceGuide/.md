=== PAGE 2: SYSTEM PURPOSE AND SCOPE ===
Beat the Heat is a web-based system that receives weather information, computes
heat-index conditions, produces health advisories, and presents role-based
dashboards and notifications for a school community.

In scope
- React and Vite frontend.
- Node.js and TypeScript backend API.
- Supabase/PostgreSQL data services and row-level security.
- Weather retrieval, heat-index calculation, advisory generation, and AI logs.
- Authentication, role permissions, incidents, announcements, and messages.
- Operational logs, database backups, migrations, and recovery.

Out of scope
This guide does not replace school emergency protocols, medical advice, vendor
documentation, or the institution's information-security policy.

Manual organization
Chapters 1–5 cover introduction and scope, platform and system overview,
preventive maintenance, corrective troubleshooting, and recovery or general
procedures. The appendices contain evidence templates and acceptance checklists.
This follows the professor's maintenance-manual reference while adapting the
procedures to Beat the Heat.

=== PAGE 4: MAINTENANCE CLASSIFICATION ===
Corrective maintenance fixes a confirmed defect, such as a failed API request,
incorrect advisory text, or broken dashboard action.

Adaptive maintenance changes the system for a new browser, Node.js version,
weather provider, school policy, or database platform.

Perfective maintenance improves performance, usability, reporting, or clarity
without changing the intended safety behavior.

Preventive maintenance reduces future failures through backups, dependency
updates, log review, database cleanup, monitoring, and restore drills.

Each ticket should identify the category, impact, owner, start time, end time,
actions taken, validation result, and rollback option.

3. Export or back up the affected data.

6. Verify counts and application behavior.
7. Record the result.

Preserve audit, incident, and safety-related evidence according to institutional

Procedure

4. Test the proposed index in staging.

6. Apply a versioned migration if approved.
7. Monitor after release.

=== PAGE 21: BACKUP POLICY ===
CHAPTER 3: DATABASE MAINTENANCE AND BACKUP
Backups protect against accidental deletion, failed migration, corruption,
provider outage, and deployment mistakes. Define recovery point objective and
recovery time objective with the project adviser or system owner.

Each backup record should include:
- Backup identifier and creation time.
- Environment and database provider.
- Tool and command or dashboard action.
- Encrypted storage location.
- Retention expiration.
- Verification result.
- Person responsible.

At least one backup copy should be stored separately from the live database.

=== PAGE 22: MYSQL BACKUP ===
Use the approved MySQL client and credentials with minimum required privilege.
Export schema and data using a consistent character set and timestamped file
name.

Procedure
1. Confirm the source database and maintenance window.
2. Verify available storage and backup destination.
3. Run the approved logical dump command.
4. Record the command without recording its password.
5. Check the exit status and file size.
6. Compress and encrypt the dump.
7. Calculate a checksum.
8. Test the file in an isolated restore environment.

Do not overwrite the previous verified backup.

=== PAGE 23: ORACLE LITE BACKUP ===
Confirm the exact Oracle Lite tool and version used by the school because
commands vary between installations. Stop or quiesce writes when required by
the tool's documentation.

Procedure
1. Confirm the database service and storage path.
2. Use the approved export or backup utility.
3. Include schema objects and required data.
4. Save the output with date, environment, and version.
5. Verify the export log and object count.
6. Encrypt and store the backup separately.
7. Perform a sample restore test.

Attach the vendor command reference to the maintenance record, not to the
production database.

=== PAGE 24: MSSQL BACKUP ===
Use SQL Server Management Studio or the approved command-line tool. A full
backup should be followed by the required differential or transaction-log plan.

Procedure
1. Confirm the selected database and recovery model.
2. Choose a verified backup destination.
3. Run a full backup with checksum when supported.
4. Verify completion and backup history.
5. Copy the file to protected storage.
6. Test restore with a different database name.
7. Record media, checksum, and restore result.

Protect `.bak` and transaction-log files as sensitive data.

=== PAGE 25: MS ACCESS 2010 BACKUP ===
Close active editing sessions before copying an Access database. A file copy
made while the database is open may be inconsistent.

Procedure
1. Notify users of the maintenance window.
2. Confirm no one is editing the file.
3. Compact and repair only after an approved backup.
4. Copy the `.accdb` or `.mdb` file to a dated folder.
5. Encrypt the backup and restrict access.
6. Open a copy to verify it is readable.
7. Record file size, timestamp, and verification result.

Never store an Access backup in a publicly served web directory.

=== PAGE 26: POSTGRESQL BACKUP ===
For PostgreSQL or Supabase, use the provider-approved export or PostgreSQL

Procedure
1. Confirm the project and database target.
2. Create a timestamped logical backup.
3. Verify tables, functions, views, policies, and sequences as applicable.
4. Encrypt the backup.
5. Store it separately from the live project.
6. Restore into an isolated test database.
7. Run application smoke tests against the restored copy.

Keep service-role keys out of commands, screenshots, and backup filenames.

=== PAGE 28: DBASE III BACKUP ===
Confirm the legacy dBase III file format and any memo or index files used by the

Procedure
1. Close the application using the files.
2. Identify `.dbf`, memo, and index files.
3. Copy the complete set to a dated backup folder.
4. Verify file names, sizes, and timestamps.
5. Compress and encrypt the backup.
6. Open a copy with the approved compatible tool.
7. Record the result and retain the original files unchanged.

=== PAGE 29: BACKUP VERIFICATION ===
A successful backup command does not prove that the backup is usable.

Verification checklist
- File exists at the intended location.
- File size is plausible compared with the source.
- Checksum is recorded.
- Backup is encrypted and access-restricted.
- Schema and expected table counts are present.
- A sample record or report is readable.
- A restore test has a recorded result.
- Retention and deletion dates are known.

Mark a backup as verified only after the operator signs or initials the record.

=== PAGE 30: RESTORE READINESS ===
Before a restore, identify the incident, target environment, desired restore
point, data owner, and approval. A production restore can overwrite newer data.

Preparation
1. Stop or restrict writes when authorized.
2. Preserve current logs and take a last-resort snapshot if possible.
3. Locate the latest verified backup before the incident.
4. Confirm encryption access and checksum.
5. Prepare a separate restore target first.
6. Define validation queries and user acceptance checks.

If the backup is unverified or corrupted, do not claim recovery is complete.

=== PAGE 38: DATABASE MIGRATION PLANNING ===
Migration may mean moving the current database to a new platform or applying a
versioned schema change. Both require inventory and rollback planning.

Planning checklist
- Source and target platform and versions.
- Tables, columns, keys, indexes, policies, views, functions, and triggers.
- Data types and unsupported features.
- Character set, time zone, and null behavior.
- Application connection changes.
- Downtime and communication plan.
- Validation queries and rollback method.

Never begin a production migration without a verified backup.

=== PAGE 39: DATABASE MIGRATION PROCEDURE ===
1. Export the source database and record the manifest.
2. Create the target schema through approved migrations.
3. Transform incompatible types in a controlled script.
4. Import data in dependency order.
5. Recreate indexes, policies, functions, views, and triggers.
6. Compare row counts, totals, timestamps, and representative records.
7. Point staging to the target and run application tests.
8. Schedule and execute production cutover.
9. Monitor and retain the source for rollback.

=== PAGE 40: MIGRATION VALIDATION ===
Validate both technical and business behavior.

Technical checks
- All expected tables and columns exist.
- Primary and foreign keys are valid.
- Policies allow intended roles and deny unauthorized access.
- Functions, views, triggers, and indexes work.
- Application connections use the target.

Business checks
- Heat readings show correct units and timestamps.
- Advisories match the configured thresholds.
- Notifications and incidents remain linked to the correct users or schools.
- Reports and dashboards show expected totals.

Record mismatches instead of silently correcting them.

=== PAGE 44: LOGGING AND MONITORING ===
Review application, database, deployment, and provider logs on a planned

Log review procedure
1. Select the time window and environment.
2. Filter by severity and affected component.
3. Correlate timestamps and request identifiers.
4. Remove or redact sensitive values from reports.
5. Open an incident for recurring or high-impact errors.
6. Confirm resolution with a new observation.

Retain logs according to the approved policy.

=== PAGE 45: SECURITY MAINTENANCE ===
Security maintenance includes dependency review, secret rotation, access review,
HTTPS verification, CORS review, rate-limit checks, and backup access review.

Immediately rotate a credential if it may have been exposed. Update dependent
services, verify authentication, and document the rotation without recording
the secret itself.

Review administrator access more often than ordinary user access. Remove stale
accounts and unused service credentials.

=== PAGE 46: TROUBLESHOOTING MATRIX ===
Frontend does not load: check deployment status, browser console, API URL,
network access, and build output.

Login fails: check authentication provider status, user state, redirect settings,
clock synchronization, and safe server logs.

Weather is missing: check provider response, credentials, rate limits, units,
timeout handling, and cached data.

Advisory is incorrect: verify input units, threshold configuration, calculation
service, model version, and audit records.

Database request fails: check connectivity, migration status, policy decision,
query shape, timeout, and service logs.

Alarm and severity handling
Classify a finding as CRITICAL when a safety-related advisory is unavailable or
incorrect, production data is at risk, or the complete service is down. Classify
it as MAJOR when a role, feature, provider integration, or repeated job is
unavailable but a safe workaround exists. Classify it as MINOR when the issue
has limited user impact and does not affect data integrity or safety. Record the
severity, start time, affected users, escalation target, and next update.

=== PAGE 47: INCIDENT RESPONSE AND ROLLBACK ===
For a high-impact failure:
1. Notify the responsible owner.
2. Preserve logs and current configuration.
3. Identify affected users and functions.
4. Disable only the unsafe feature if possible.
5. Restore the last known-good release or database state.
6. Validate authentication, heat data, advisories, and notifications.
7. Communicate service status.
8. Document cause, impact, recovery, and prevention.

Rollback must be a controlled release, not an undocumented file replacement.

Replacement and recovery procedures
Beat the Heat is primarily software, so field-replaceable hardware procedures
are replaced by controlled replacement of a failed service, deployment artifact,
configuration, database target, or provider credential. Preserve the failed
artifact and logs, deploy the known-good replacement, validate the main user
flows, and document the old and new identifiers. Do not delete the failed
artifact until the incident is closed.

=== PAGE 48: MAINTENANCE SCHEDULE AND CHECKLIST ===
Daily: check availability, failed jobs, weather freshness, critical errors, and
notification failures.

Weekly: review accounts, database health, backups, storage, incident status,
and dependency alerts.

Monthly: test a restore, review policies and indexes, rotate planned secrets,
review retention, and verify disaster-recovery contacts.

Preventive maintenance record
Daily checks should include service availability, login, weather freshness,
heat-index calculation, advisory display, notification queue, and critical
errors. Monthly checks should include a restore drill, dependency review,
account review, policy review, log-retention review, network/time verification,
and an update of the contact and escalation list.

Per release: record version, run tests, back up data, deploy, smoke test,
monitor, and close the release record.

Checklist fields: task, owner, date, result, evidence link, defect, corrective
action, reviewer, and next due date.
